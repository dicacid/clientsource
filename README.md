# Prospect Finder B2B

A self-hosted B2B prospecting CRM for small teams. Manage companies and contacts, research public company websites, and optionally use OpenRouter to draft evidence-based outreach.

[![Build](https://github.com/dicacid/clientsource/actions/workflows/ci.yml/badge.svg)](https://github.com/dicacid/clientsource/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

> **Status:** early-stage and usable, but not yet security-audited for large multi-tenant deployments. Read [Security](SECURITY.md) and [Architecture](docs/ARCHITECTURE.md) before exposing an instance to untrusted users.

## What it does

- Stores companies, contacts, activities, follow-ups and workspace members.
- Imports and exports CRM data as CSV.
- Analyzes your business website to understand what you sell and who you should target.
- Suggests matching companies and checks that their public websites are live.
- Reads a bounded set of public pages to find evidence, decision-makers and published email addresses.
- Drafts outreach from observed target facts, verified sender facts and operator-approved claims.
- Opens drafts in your own email client; it does **not** send email itself.
- Uses OpenRouter optionally. The core CRM works without an AI key.

## Stack

| Layer | Technology |
| --- | --- |
| App | React 19, TypeScript, TanStack Start |
| UI | Tailwind CSS, Radix UI |
| Server | Node.js / Nitro |
| Persistence | Redis-compatible key-value store |
| Authentication | App-native email/password auth, scrypt password hashes, signed sessions |
| Optional AI | OpenRouter |
| Current host | Render |

The folder `src/integrations/render` is historical. The persistence code uses the Redis protocol and can run with local Redis or another compatible managed service.

## Quick start

### Requirements

- Git
- Node.js 20+
- npm
- Docker Desktop **or** another Redis-compatible server

### 1. Clone

```bash
git clone https://github.com/dicacid/clientsource.git
cd clientsource
```

### 2. Start Redis

```bash
docker compose up -d redis
```

If you already run Redis, point `REDIS_URL` at it instead.

### 3. Create your environment file

```bash
cp .env.example .env
```

Generate a strong session secret:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Paste that value into `SESSION_SECRET`.

`OPENROUTER_API_KEY` is optional. Leave it blank if you only want the CRM.

### 4. Install and run

```bash
npm install
npm run dev
```

Open the local URL printed by Vite.

### 5. First run

1. Open `/auth`.
2. Create an account and sign in.
3. The first user can create the workspace and becomes its owner.
4. Additional users must be invited by exact email address before joining.

## Environment variables

| Variable | Required | Purpose |
| --- | --- | --- |
| `REDIS_URL` | Yes | Redis-compatible connection string. Local default: `redis://localhost:6379`. |
| `SESSION_SECRET` | Yes | Secret used to sign sessions. Use at least 32 random bytes. |
| `OPENROUTER_API_KEY` | No | Enables Prospect Finder AI. Keep it server-side only. |

Never commit `.env`, API keys, Redis credentials or session secrets.

## Deployment

Production build:

```bash
npm install
npm run build
node .output/server/index.mjs
```

For Render and generic deployment instructions, see [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md).

The app exposes `/health`, which performs a real datastore write/read/delete probe and reports whether AI is configured without exposing secrets.

## Current limitations

- State is stored as one versioned JSON document in Redis.
- Write serialization is process-local; run **one web instance** unless you add distributed locking/transactions or a different persistence adapter.
- Sessions currently use a signed bearer token in browser local storage. Moving to HttpOnly cookies is a planned hardening change.
- Invites are email-matched but there is no built-in email verification yet.
- “Domestic” prospecting currently means Australia.
- Public-site fetching rejects local/private/link-local destinations and validates every redirect before following it. A hardened custom DNS transport is still recommended for high-risk multi-tenant deployments.

See [roadmap.md](roadmap.md).

## Lovable compatibility

This repository is currently connected to a Lovable project and still uses `@lovable.dev/vite-tanstack-config` as a build-time dependency. Lovable is **not required at runtime**.

While that project remains connected, avoid rewriting published Git history unless you intentionally plan to reconnect it afterwards.

## Responsible use

Prospect suggestions are AI-assisted and should be reviewed by a human. Contacts and email addresses should come only from public pages. Operators are responsible for applicable privacy, anti-spam and marketing laws and for honoring opt-out requests.
